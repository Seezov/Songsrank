# Синк між пристроями — дизайн

Дата: 2026-10-07
Статус: чернетка на погодження

## Мета

Рейтинги, бої, видалені пісні й рішення по дублікатах автоматично сходяться між
телефоном і ПК (і будь-якими іншими пристроями) без ручного перенесення бекапів.
Бої, зіграні на двох пристроях до синхронізації, не губляться.

Фундамент під наступну фічу — інші люди зі своїми піснями: кожен користувач має
власний обліковий запис і власні дані.

### Критерії успіху

- Бій на телефоні з'являється на відкритому ПК за кілька секунд без перезавантаження.
- Телефон офлайн + ПК онлайн, на обох по кілька боїв → після появи мережі на обох
  однаковий стан, у якому враховані всі бої з обох пристроїв.
- Без входу сайт працює точно як зараз (лише локально).
- Інший Google-акаунт не може прочитати чи змінити чужі дані.

### Поза скоупом

- Історія версій у хмарі / відкат до старого стану.
- Будь-яка взаємодія між користувачами (спільні рейтинги, порівняння).
- Синк Spotify-токена і Client ID (токен отримується на кожному пристрої; Client ID
  уже має значення за замовчуванням).
- Офлайн-кеш самого Firestore SDK (офлайн-режим робимо власним журналом).

## Архітектура

### Сховище і вхід

- Окремий Firebase-проект `songsrank`, план Spark (безкоштовний).
- Firebase Authentication з провайдером Google, вхід через `signInWithPopup`.
- Cloud Firestore, один документ на користувача: `users/{uid}`.
- Firebase JS SDK (модульний) підвантажується з `https://www.gstatic.com/firebasejs/<версія>/`
  через динамічний `import()` лише тоді, коли користувач увійшов або тисне «Увійти».
  Без входу SDK не завантажується зовсім.
- Конфіг веб-застосунку Firebase (apiKey, projectId тощо) публічний за задумом і
  вшивається в код.

Правила Firestore:

```
rules_version = '2';
service cloud.firestore {
  match /databases/{db}/documents {
    match /users/{uid} {
      allow read, write: if request.auth != null && request.auth.uid == uid;
    }
  }
}
```

### Документ у хмарі

`users/{uid}`:

| поле        | тип        | зміст |
|-------------|------------|-------|
| `v`         | number     | версія, +1 на кожен запис |
| `data`      | Bytes      | gzip(JSON стану) — `tracks`, `fights`, `removed`, `resolved` |
| `schema`    | number     | версія формату стану, зараз `1` |
| `updatedAt` | timestamp  | серверний час запису |
| `device`    | string     | короткий опис пристрою, що записав (для діагностики) |

Стиснення — `CompressionStream('gzip')` у браузері. Очікуваний розмір для ~2 140
пісень: ~150–200 КБ (ліміт документа Firestore — 1 МБ). Якщо стиснений стан
перевищує 900 КБ, синк зупиняється з помилкою в індикаторі, локальні дані не
страждають.

`history` (стек для Undo) у хмару не потрапляє — він локальний для пристрою.

### Локальні дані

| ключ localStorage | зміст |
|-------------------|-------|
| `sfn.state`       | поточний стан (як зараз) = `base` + всі `pending` дії |
| `sfn.sync`        | `{ uid, v }` — чий і якої версії `base`; немає ключа → синк вимкнено |
| `sfn.base`        | останній знімок, узгоджений із хмарою (версія `v`) |
| `sfn.pending`     | масив дій, ще не записаних у хмару |

## Журнал дій

Кожна зміна стану — це дія `{ id, type, at, ...payload }`, де `id` — випадковий
рядок, `at` — ISO-час створення. Одна чиста функція `applyOp(state, op)` застосовує
будь-яку дію і повертає опис ефекту (для Undo). Усі нинішні мутації в коді
переходять на `dispatch(op)` = `applyOp` на `state` + додати в `pending` + `save()` +
запланувати синк.

Вимоги до `applyOp`:
- **детермінована**: не викликає `Date.now()`, `Math.random()`, мережу — усе потрібне
  лежить у дії;
- **толерантна**: якщо пісні, на яку посилається дія, немає (видалили на іншому
  пристрої), дія або пропускає відсутню частину, або стає no-op; ніколи не падає;
- побічні ефекти в Spotify (unlike / like) виконує лише той пристрій, що створив дію,
  під час `dispatch`, а не `applyOp`.

Типи дій:

| type          | payload | що робить |
|---------------|---------|-----------|
| `fight`       | `a, b, score` | Elo-оновлення як зараз `applyResult`; рахує `da, db` від поточних рейтингів |
| `unfight`     | `a, b, score, da, db` | віднімає `da/db`, лічильники ігор/перемог, `fights − 1` |
| `remove`      | `trackId` | переносить пісню в `removed` (`removedAt = at`) |
| `restore`     | `trackId` | як нинішній `restoreSong` |
| `markUnliked` | `trackIds` | ставить `unliked = true` у `removed` |
| `merge`       | `sig, keepId, removeIds` | як нинішній `mergeDupes` |
| `removeVersions` | `sig, keepId, removeIds` | як нинішній `removeVersions` |
| `distinct`    | `sig` | позначає групу як «не дублі» |
| `unresolve`   | `sig` | як нинішній `unresolve` |
| `import`      | `tracks, removeMissing` | як нинішній `merge(incoming, removeMissing)` (CSV і синк лайків) |
| `cover`       | `trackId, url` | обкладинка з oEmbed |
| `reset`       | — | усі рейтинги в 1500, `fights = 0` |
| `replace`     | `state` | повна заміна стану (відновлення бекапу) |

## Алгоритм синку

`syncNow()` (одночасно виконується не більше одного):

1. Запам'ятати `n = pending.length`, `ops = pending.slice(0, n)`.
2. Транзакція Firestore:
   - прочитати `users/{uid}`; `remoteV = doc?.v ?? 0`;
   - якщо `remoteV === sync.v` → `next = state` (наш стан уже = база + дії);
   - інакше → `next = replay(decode(doc.data), ops)`;
   - якщо `n === 0` і `remoteV === sync.v` → нічого не писати;
   - записати `{ v: remoteV + 1, data: encode(next), ... }`.
3. Після успіху: `base = next`, `sync.v = remoteV + 1` (або `remoteV`, якщо не писали),
   `pending = pending.slice(n)` (дії, створені під час транзакції, лишаються),
   `state = replay(base, pending)`, перемалювати поточний екран.
4. Помилка мережі → нічого не змінюємо, `pending` лишається, індикатор «Офлайн».

`replay(s, ops)` = послідовно `applyOp` для кожної дії на копії `s`.

Коли запускається:
- одразу після входу і при відкритті сайту (якщо вже увійшли);
- через 5 с після останньої дії (debounce);
- на `visibilitychange` → `hidden` (згорнули вкладку);
- на подію `online`;
- з `onSnapshot`: прийшла версія `> sync.v` — якщо `pending` порожній, просто
  приймаємо її як нову базу і стан; інакше запускаємо `syncNow()`.

Якщо під час прийняття віддаленої версії на екрані бою одна з пісень поточної пари
зникла, пара перевибирається.

## Undo

`state.history` зберігає посилання на дії: `{ opId, kind, ... }` (кілька останніх, як зараз до 200).

- Дія ще в `pending` → прибрати її з `pending`, `state = replay(base, pending)`.
- Дія вже в хмарі → `dispatch` зворотної дії: для `fight` — `unfight` з `da/db`, які
  ця дія дала при останньому застосуванні на цьому пристрої (зберігаються в записі
  history і оновлюються після кожного replay); для `remove` — `restore`.

Spotify-побічні ефекти Undo (повторний лайк) — як зараз.

## Перший вхід і особливі випадки

Після входу, коли `sfn.sync` відсутній або належить іншому `uid`:

| хмара | локально | дія |
|-------|----------|-----|
| порожня | порожньо | нічого, просто ввімкнути синк |
| порожня | є пісні | записати локальний стан як `v = 1` |
| є дані | порожньо | прийняти хмарний стан |
| є дані | є пісні | діалог на сторінці: «Залишити дані з хмари» / «Замінити хмару даними з цього пристрою» (з кількістю пісень і боїв у кожному варіанті) |

- **Вихід** (Sign out): локальні дані лишаються, `sfn.sync`, `sfn.base`, `sfn.pending`
  видаляються. Неусинхронізовані дії перед виходом намагаємось відправити.
- **Remove all data**: як зараз чистить пристрій, плюс виходить з акаунта. Хмару не чіпає.
- **Restore backup** при ввімкненому синку → підтвердження «Це замінить дані на всіх
  пристроях», далі дія `replace`.
- **Reset ratings** → дія `reset` (поширюється на всі пристрої, текст підтвердження
  про це каже).
- `schema` у хмарі новіша за підтримувану кодом → синк зупиняється з проханням
  оновити сторінку.

## UI

- **Індикатор у шапці** (праворуч від меню, на телефоні — поруч із назвою): невеликий
  текст/іконка — «Synced», «Syncing…», «Offline · N pending», «Sync error». Без входу
  не показується.
- **Settings → Account** (новий блок на початку):
  - не ввійшов: пояснення одним реченням + кнопка «Sign in with Google»;
  - увійшов: email, час останнього синку, «Sync now», «Sign out».
- **Стартовий екран** (порожній пристрій): блок «Already ranking on another device?
  Sign in with Google» поруч із наявним «Restore a backup».
- Діалог першого входу — `<dialog>` на сторінці, не `confirm()`.
- Тексти інтерфейсу англійською, як решта сайту.

## Структура коду

- Новий файл `core.js` — чисті функції без DOM: `applyOp`, `replay`, Elo-хелпери,
  `encodeState`/`decodeState`. Підключається звичайним `<script src="core.js">` і
  експортує в `module.exports`, коли запущений у Node.
- `index.html` — UI, `dispatch`, Spotify, і новий блок `sync` (Firebase-завантаження,
  вхід, `syncNow`, `onSnapshot`, індикатор).
- Нинішні мутації (`applyResult`, `removeSong`, `restoreSong`, `mergeDupes`,
  `removeVersions`, `unresolve`, «Not duplicates», `merge`, обкладинки, reset, restore
  backup, `unlikeInSpotify`) переписуються на `dispatch(op)`; їхня логіка переїжджає в
  `applyOp`.
- Наявні бекапи і `sfn.state` лишаються сумісними: формат стану не змінюється.

## Налаштування Firebase (робить власник, ~5 хв)

1. console.firebase.google.com → Add project → `songsrank`, Google Analytics не потрібен.
2. Build → Authentication → Get started → Sign-in method → Google → Enable.
3. Authentication → Settings → Authorized domains → додати `seezov.github.io` і `127.0.0.1`.
4. Build → Firestore Database → Create database → production mode, регіон `eur3`
   (або `europe-central2`).
5. Firestore → Rules → вставити правила з цього документа → Publish.
6. Project settings → Your apps → Web (`</>`) → зареєструвати `songsrank-web` →
   скопіювати об'єкт `firebaseConfig` і передати для вшивання в код.

Квоти Spark (50 тис. читань і 20 тис. записів на день) з debounce 5 с у кілька
порядків більші за потреби.

## Помилки

| ситуація | поведінка |
|----------|-----------|
| нема мережі / Firestore недоступний | дії накопичуються в `pending`, індикатор «Offline · N pending», повтор на `online`, при поверненні у вкладку і щохвилини, поки вкладка видима |
| popup входу заблоковано / закрито | повідомлення з кнопкою спробувати ще раз |
| стиснений стан > 900 КБ | «Sync error: data too large», локально все працює |
| пошкоджені дані в хмарі (decode падає) | синк зупиняється, локальні дані не перезаписуються, повідомлення |
| сесія Firebase протухла | SDK оновлює сам; якщо ні — індикатор «Sign in again» |

## Тестування

Автоматичні тести на `node:test` (`tests/sync.test.js`), без браузера і Firebase —
хмара імітується об'єктом `{ v, data }` з тією самою логікою транзакції:

- `applyOp` для кожного типу дії дає той самий результат, що нинішній код (порівняння
  на фікстурі з кількох пісень);
- `applyOp` на стані без потрібних пісень не падає;
- два «пристрої» з однієї бази паралельно грають бої, видаляють пісні, зливають
  дублі → синк одного, потім другого → у результаті всі бої (`fights` = сума), обидва
  видалення, обидва злиття; стани обох пристроїв після синку однакові;
- Undo неусинхронізованої дії прибирає її; Undo усинхронізованого бою дає `unfight`,
  який повертає рейтинги;
- дії, додані під час «транзакції», не губляться;
- `encodeState`/`decodeState` — круговий тест і розмір для 2 500 згенерованих пісень
  < 900 КБ.

Ручна перевірка після викладки: вхід на ПК (127.0.0.1:8888) і телефоні; діалог
першого входу; бій на телефоні з'являється на ПК; режим польоту на телефоні + бої на
обох → злиття; Undo; Restore backup поширюється на інший пристрій.
